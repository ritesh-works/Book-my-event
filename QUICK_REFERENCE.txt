CORE MECHANISM (30-second pitch):
  "Instead of SELECT-then-UPDATE (which races), we do atomic UPDATE with WHERE:
   UPDATE seats SET status='CONFIRMED' WHERE status='AVAILABLE'
   Only one thread's WHERE is satisfied. Others get 0 rows → 409.
   No race condition. Atomic decision at database level."

API ENDPOINTS:

RESPONSE CODES:

DATABASE SCHEMA (Key Points):
  Seats table:
    - (show_id, seat_number) UNIQUE → can't create duplicate
    - status ENUM (AVAILABLE|HELD|CONFIRMED)
    - Indexes on (show_id, status) for fast filtering
  
  Reservations table:
    - (user_id, idempotency_key, show_id) UNIQUE → exactly-once per key
    - Tracks amount_paise (integer, never float)
  
  ReservationSeats (join table):
    - Links reservations to the actual seats

TRANSACTION ISOLATION:
  Level: REPEATABLE_READ (PostgreSQL default)
  Effect: Prevents dirty reads and non-repeatable reads
  Deadlock prevention: Sort seats alphabetically before locking

IDEMPOTENCY FLOW:
  Client sends: {seats: ["A12"], idempotency_key: "key_xyz"}
  
  Server checks: SELECT * FROM reservations WHERE user_id=? AND key=?
  If found: Return existing reservation (no new transaction)
  If not: Proceed with reservation, store key for future replays
  
  Safety: Same key always → same result (even if client retries 100x)

ERROR SCENARIOS (How They're Handled):
  Race for seat A12:
    Thread A: UPDATE → 1 row affected → 201 Created
    Thread B: UPDATE → 0 rows affected → 409 Conflict
  
  User exceeds limit:
    User has 4 confirmed, tries 5th
    Count check in same transaction → 409 Conflict
  
  Idempotent replay:
    Same key as before → Found in DB → 201 + original reservation
  
  Database offline:
    /health/ready → DOWN
    Load balancer removes this instance
    New requests fail immediately with 503
